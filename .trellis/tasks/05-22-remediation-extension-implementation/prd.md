# 整改与扩展任务拆分与实施

## Goal

基于 `docs/debug/remediation-extension-design/rectification-and-extension-design.md`，将整改与扩展路线图拆分为可独立验证的子任务，在 `docs/tasks/` 下输出任务文档，并按确认后的优先级逐个实现。每个已实现子任务必须完成测试、复核，并输出完成报告。

## User Value

- 将大型整改路线图转化为可执行、可追踪、可验收的工程任务。
- 优先消除公开图床部署中的安全、稳定性和数据一致性风险。
- 为后续扩展能力保留清晰的实施顺序、验证命令和完成报告。

## Confirmed Facts

- 源设计文档已存在：`docs/debug/remediation-extension-design/rectification-and-extension-design.md`。
- 文档已将事项分为 P0 / P1 / P2：
  - P0 约 24 人日，包含上传资源保护、文件真实性校验、URL 上传 SSRF 防护、Token 治理、默认密码安全改造、软删除回收站、SQLite 核心索引、配置审计日志、存储健康检查。
  - P1 约 50 人日，包含异步转换队列、原图备份、多格式输出、图片审核、批量打包下载、存储回退、Prometheus 指标、请求追踪、滥用统计聚合。
  - P2 约 57 人日，包含 JPEG-XL、短链、相册、访问统计、图片处理、存储迁移/API Key/CDN 预热等。
- 当前后端架构为 Gin + SQLite + Redis + 多存储 Provider；已有上传、AVIF 转换、MD5 去重、IP 封禁、运行时设置、Cloudflare 单 URL 清理等能力。
- 当前前端架构为 SvelteKit + Svelte 5 + Tailwind，管理后台已有图片、安全、设置、公告等页面。
- 当前工作区已有与本任务无关的未提交前端变更：`frontend/src/lib/i18n.ts`、`frontend/src/routes/+error.svelte`，实施时不得混入本任务提交。

## Requirements

- 在 `docs/tasks/` 下输出 P0/P1/P2 全量子任务文档，至少包含：目标、范围、依赖、实施要点、验收标准、测试/复核要求、完成报告模板。
- 本轮代码实现范围限定为 P0 安全与稳定性基线；P1/P2 仅拆分为后续任务文档，不进入本轮实现。
- 子任务需按优先级和依赖关系拆分，避免把多个不可同时验收的大功能混在一个任务中。
- 每个实际实施的 P0 子任务必须：
  - 更新对应代码/文档。
  - 运行与改动范围匹配的测试和校验命令。
  - 完成复核，确认需求、设计、代码、测试一致。
  - 在 `docs/tasks/` 对应任务文档中补充完成报告。
- 实施顺序需尊重依赖：安全与稳定性基线优先于大型扩展；数据模型/迁移优先于 UI 管理能力。
- 不得覆盖或提交用户/其他任务的未提交变更。

## Acceptance Criteria

- [ ] `docs/tasks/` 中存在清晰的任务拆分文档，并能映射回源设计文档的 P0/P1/P2 路线图。
- [ ] 每个任务文档包含可测试的验收标准、推荐验证命令和完成报告区。
- [ ] 已确认本轮实际实施范围，并在 Trellis `design.md` / `implement.md` 中记录边界、顺序和验证策略。
- [ ] 每个已实施子任务均有通过的测试/校验记录和复核结论。
- [ ] 最终输出总完成报告，列明已完成、未完成、风险、后续任务。

## Out of Scope Until Explicitly Approved

- 一次性实现 P0 + P1 + P2 全部功能。
- 改动与本任务无关的全局错误页前端文件。
- 引入完整账户体系或商业化权限模型，除非对应子任务被明确纳入本轮范围。
- 大规模重写上传 API 协议，除非选择异步转换队列作为本轮范围。
